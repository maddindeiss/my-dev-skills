# Requested skills across the delivery chain

Requested skills is an optional field, separate from the completed specification and plan. A request with no skill selection proceeds normally. When the user selects a skill, applying it within its stated scope becomes an explicit execution requirement. Carry them through main request → worker-orchestrator run → worker assignment → test evidence → independent review → final delivery. Never drop them when restarting, replacing a worker, or sending a repair assignment.

## Record

Omit the field, leave it empty, or use `Requested skills: None` for an initial request with no selections; none of these blocks dispatch. During updates, omission means no change to previously selected skills. Explicitly clearing existing selections needs a user instruction. When selections exist, record this table in request.md and run.md with the current skills revision:

| ID | Skill | Resolved source | Applies to | Roles | User instruction |
| --- | --- | --- | --- | --- | --- |
| RS-001 | impeccable | Absolute SKILL.md path or supported skill resource ID, plus version/hash when available | UI changes in this request, including existing UI work | implementation, verification, review criteria | Chat/message reference or directly observed user instruction |

Initialize the skills revision to RS-0 for an empty selection; omit per-skill evidence when there is nothing to apply. Give each selected entry a stable ID. Keep the user's requested skill name and scope. Resolve its installed source before assignment; do not assume a global skill is readable in every worker environment. Forward the applicable entries and current revision explicitly, not only a link to the parent's chat. For unaffected tasks, record `Not applicable` with a reason, such as backend-only work. An explicit user removal is recorded as an update, never inferred from omission.

The worker coordinator and assigned agent read applicable SKILL.md instructions and any necessary references. If unavailable, search installed sources and report the missing capability; block affected work until resolved rather than silently substituting another skill or claiming compliance. Skill selection does not authorize installation, publication, or other side effects beyond the user's request. Skill instructions remain subject to host policies, user scope, and the agent's role. A reviewer reads the skill for applicable standards and checks evidence without executing editing or publishing steps. An irreconcilable conflict returns a concrete blocker.

## User instructions received by main

Main records the requirement, advances its canonical skills revision (`RS-1`, `RS-2`, ...), and sends the full current requirements and revision to the worker orchestrator. The coordinator records the revision, determines affected assignments, and forwards the requirements to existing or new workers and reviewers. Main does not read the whole skill or worker logs merely to relay the requirement.

## User instructions received directly by the worker orchestrator

1. Accept a directly observed user instruction in that chat. Record a durable update before dispatch: unique update ID (coordinator ID plus a persisted sequence), request ID, base skills revision, add/change/remove operation, exact requested skill/scope, human-message reference, affected tasks, and status `Pending main acknowledgment`. The main remains the sole writer of request.md and the canonical skills revision.
2. Apply the instruction to affected work immediately, without waiting for permission already given by the user. Pause obsolete affected assignments, forward the revised requirements, and recheck already-produced work. Use an effective requirements identifier such as `RS-2 + coordinator-7` while the update awaits acknowledgment. Continue unaffected work. If the skill implies changed product behavior/design, pause that scope for the separate spec/plan phase instead of silently revising it.
3. Publish a compact `Skills update` checkpoint immediately, including update ID, base revision, change, user-message reference, and affected work. Keep it in run.md's pending-update list and in subsequent checkpoints until main acknowledges it. Do not wait until final delivery to report it. If direct messaging back to main is authorized by the actual user and supported, send that compact update to the recorded main chat ID/host too. Otherwise main collects it through snapshots; do not claim synchronization just because it was emitted.
4. Main consumes the event idempotently, records the requirement in request.md, advances the canonical skills revision, and acknowledges the update ID plus the resulting revision and full requirements to the worker orchestrator. Do not ask the user to repeat a compatible directly given instruction. Verify its human provenance through the originating chat when needed, without reading unrelated transcripts.
5. Concurrent changes are reconciled against the event's base revision: combine compatible updates, preserve unrelated requirements, and never replace current state with an older full snapshot. If two user instructions disagree and their order or intent is unclear, pause only the affected scope and ask for resolution. Persist each event acknowledgment and its resulting revision. A duplicate event receives acknowledgment of that same event plus the latest canonical revision and full current selections, without another revision or repair round; do not replay its old selections as current state.
6. The worker orchestrator marks the event acknowledged only on receipt of main's matching acknowledgment. Separate the revision at which the event was accepted from the current canonical revision. Never roll back to an older canonical revision or restore a skill removed by a newer instruction; accept an event acknowledgment without replacing a newer local canonical snapshot. Equal revisions with different content are a synchronization error to resolve with main. Carry forward equivalent pending-era evidence only when the latest selections still match, mapping the event to the acknowledged entry. If acknowledgment changes the actual requirement, invalidate affected evidence again. Clear only the acknowledged event, retaining other pending updates and their effective selections on top of the latest canonical snapshot. Persist mappings and pending events across resumes and coordinator replacement.

Main may be idle or unavailable; a checkpoint alone cannot wake every host. Keep the event pending, preserve the worker progress, and tell the user synchronization is pending. Final completion or merge waits for acknowledgment; the main reconciles pending events on resume. Never bypass this by editing its request.md from the worker chat.

## Evidence and final gate

Each worker reports skill ID/source, effective revision, applicability, and concrete actions/evidence. Tests report relevant checks; reviewers report `Satisfied`, `Missing`, `Unverified`, or `Not applicable` per applicable skill requirement. A claim that a skill was used is not sufficient evidence by itself.

A new requirement invalidates affected review approvals even if the code SHA is unchanged. Recheck existing output under the skill and send the changed requirements and evidence to the existing reviewer at the applicable review gate. Preserve valid unrelated evidence. The final review and main acknowledgment bind the source SHA, request revision, skills revision, and full requirements. No completion or target update is allowed with pending skill updates, stale applicable evidence, or unresolved requested-skill blockers.
