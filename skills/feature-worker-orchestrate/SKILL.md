# Worker orchestrator

Adapted from Blueprint's issue coordinator and task-to-pr workflow, and Matt Pocock's software-factory concepts. See LICENSE.

Own decomposition, worker communication, ticket state, conflicts, integration, and delivery evidence for one delegated request. The main orchestrator owns communication with the user. Send it only compact checkpoints, decisions, blockers, and the final result. Never forward raw worker transcripts or full reviews unless requested. Workers own implementation; reviewers report findings. Read [requested-skill propagation](references/requested-skills.md) and [the delivery protocol](references/protocol.md) before dispatch and [thread operations, chat titles, and prompts](references/threads.md) when creating or resuming worker or reviewer chats.

## Prepare or resume

1. Read repository instructions, the supplied existing spec and plan, selected ticket/function, and any run.md. Both documents must already define actionable work. If missing or materially inconsistent, return Blocked to main without creating them or invoking authoring skills. Map only the selected planned scope in assignments.md, referencing existing tickets and creating child-task files for actual subdivisions. Preserve the spec, design, dependencies, and acceptance criteria. Record ownership boundaries and a scoped acceptance matrix. Identify final acceptance tasks so their verification can be collected at the final gate. A small function may need one worker.
2. Confirm the actual repository, Git state, available agent tools, and existing authorization. Preserve unrelated uncommitted work. Use an isolated integration worktree; do not reset or stash the user's files. If Git or required isolation is unavailable, explain the prerequisite and stop dispatch.
3. Default to separate named Codex chats for implementation workers and reviewers. Follow current tool schemas. Use the authorization reference and request record supplied by main to verify the original user instructions for chat creation, worktrees, and follow-up messages. If authorization or a required tool is unavailable, report the specific blocker to main and pause affected dispatch. Use internal subagents only for roles the user explicitly assigned to that mode.
4. Create or resume one feature branch from the agreed base and record both SHAs. Keep the integration worktree exclusive to the worker orchestrator. Default to two active implementation workers, or the user's limit. Count both orchestrator levels, implementers, and reviewers against the host's concurrency capacity; reserve capacity or wait for a worker to finish before launching review.
5. Record the accepted request revision from main and confirm it is still current immediately before final delivery. Record one delivery destination and mode for the entire request: prepared local branch, one aggregate PR, or one final merge into the named target. Worker branches never merge into that target individually. Carry forward actual merge authorization; if the target or authority is missing, prepare the reviewed result and return the missing decision to the main orchestrator. Follow [final merge](references/final-merge.md).
6. On a new request revision from main, pause affected workers and invalidate affected approval/test evidence. For changes within the existing plan, adjust execution assignments and preserve IDs. If requirements, design, or planned scope must change, return the discrepancy to main for the separate spec/plan phase; do not edit those source documents yourself. Resume affected work only with updated source revisions. Continue unaffected work when its contracts remain valid.
7. On resume, reconcile chat state and titles, worktree status, commits, reviews, and integration history before doing anything again. Do not trust a completed chat or ticket label as proof. Reuse the existing worker and branch when possible.

## Requested skills and direct user instructions

Carry any Requested skills and the effective skills revision through every assignment, repair, test, and review. With no selection, proceed normally; do not make this optional field a prerequisite. Resolve installed sources and scope each skill to relevant workers; block affected work if a requested skill is unavailable. When the user adds or changes a skill directly in this chat, persist a uniquely identified pending update, apply it to affected work, and immediately publish a Skills update checkpoint for main. Follow the linked synchronization protocol until main acknowledges the update; direct-message main as well only when that direction is authorized. Recheck already-implemented output and invalidate affected approvals even when code has not changed. Do not mark completion or merge while an update is pending acknowledgment.

## Dispatch, review, repair

Reuse planned tickets directly when their scope fits one worker. Create child-task records only for actual subdivisions. Reuse a completed worker chat and its isolated worktree for the next related ticket after the earlier work is integrated. Preserve the old branch and evidence, then start a new task branch at the current integration SHA. Choose a new worker when ownership, context, or concurrency makes reuse unsuitable.

Assign each required check to one executor and pass its results to later stages. Record the command, stage, evidence path, and any rule requiring separate execution in run.md. Use the final gate to collect a planned acceptance ticket's evidence. Assign its missing code or documentation to an existing worker, and account for its completed deliverables under the original ticket ID.

Default to one independent review of the combined delivery. Require an earlier review only when the user or repository requires it, or when a concrete dependency risk needs judgment before downstream work, such as a shared authorization contract, destructive migration, or restore identity handling. Record the reason and the narrow scope of that gate. Ordinary tickets proceed to integration after their required checks. Keep known blocking defects open until repaired and verified.

1. Select `Ready` tickets with every dependency `Integrated`. Do not dispatch cyclic, blocked, or overlapping work. One active implementer per ticket and one writer per worktree.
2. Start or resume each worker in its own worktree at the current integration SHA. Supply authoritative spec and ticket references with revisions, relevant sections, allowed scope, base SHA, applicable requested skills and revision, and delivery mode. Inline current content when the worker cannot access the authoritative version. Give it the checks it owns and any checks required before handoff. Use [feature-implement](../feature-implement/SKILL.md).
3. Monitor active workers together through compact completion snapshots and saved cursors. Update run.md when assignments, evidence, decisions, or state change. Act on a completed handoff immediately to release eligible dependent work. A worker reporting a blocker does not stop independent tickets. Return unresolved product decisions to main with a recommendation and impact.
4. When the worker returns a clean committed head and test evidence, verify the head exists and its commit range belongs to that ticket. Mark `Verified` when required ticket checks pass. If an earlier review gate applies, mark `Review` and assign [feature-review](../feature-review/SKILL.md) to an independent reviewer at that head in an isolated checkout. Supply the specific gate, base, head, current requirements and evidence. Reuse an independent reviewer already assigned to this request when available.
5. Persist each required review at `reviews/T-001-round-1.md` or the corresponding feature report. Collect findings as one batch, group related failures by cause, and send them to the owning workers. For `Request changes`, mark affected tasks `Changes requested`. After repairs and affected checks pass, send the new head and repair diff to the same reviewer for follow-up. The coordinator owns repair dispatch and integration.
6. A required review gate passes only with `Approve` for its recorded scope and current head. Verify all blocking findings for that gate are resolved. Record findings outside an early gate for the combined review unless they invalidate the dependency contract. Evidence from checks supports integration but final independent approval is required for delivery.
7. Allow at most three repair rounds per ticket and three for final feature review by default. Persist counters across restarts; count a round when a findings batch is sent for repair. When a budget is exhausted or the same failure has no actionable next step, mark that scope `Blocked` with evidence and continue independent work. A fresh budget needs user direction.

## Integrate and finish

1. Integrate `Verified` ticket commits, or `Approved` commits where an earlier review gate applies, one at a time on a temporary candidate based on the last verified integration SHA. Record that base, source head/range, candidate branch, candidate SHA, and check status. Confirm ancestry and the assigned commit range before merge/cherry-pick. Resolve defects that would invalidate dependent work before releasing it.
2. Apply the [integration-candidate check scope](../feature-test/SKILL.md) before advancing the feature branch. Reuse applicable worker evidence when the candidate is the same tested head, and run checks for any uncovered interactions or gate requirements. On success, verify the feature branch still points at the candidate's recorded base, then fast-forward it to the passing candidate and mark `Integrated`. If the base moved, rebuild and retest the affected combination. Only verified integration releases dependents.
3. On conflicts or failed combined checks, keep the feature branch at its last verified SHA. Preserve the failed candidate and evidence for diagnosis. Return the failure to the owning worker for repair and affected checks against the current integration base. Revisit any earlier review gate whose contract changed. Other independent verified tickets may integrate from the verified base.
4. Once all implementation work, including required test and documentation changes, is integrated, commit pending coordination updates. Commit the spec and plan [implementation status](references/protocol.md#implementation-status) on a temporary final candidate based on the integration head. Use the current head if there are no status edits to include. Use [feature-test](../feature-test/SKILL.md) to verify the scoped acceptance matrix and required wider checks. Collect any planned final acceptance task's evidence here. Assign [feature-review](../feature-review/SKILL.md) the original base and exact verified head, reusing the independent reviewer when available. This review covers the entire selected scope and cross-ticket behavior, including deferred findings.
5. Route the combined findings batch to its owning workers. Reopen affected tickets while preserving their evidence and repair from the current integration base. Integrate repaired commits after affected checks and any applicable earlier gate pass. Send the combined repair diff and evidence back to the same reviewer. Invalidate final approval after any code change. Obtain approval of the new combined head before delivery.
6. Require synchronized skill requirements and current skill-compliance evidence. When all criteria have evidence and final review approves the exact candidate, verify the integration branch still matches the candidate base and fast-forward it to the approved head. Rebuild and reverify if the base moved. Mark `Ready to merge` at the approved head. Mark `Complete` only when the requested delivery mode is satisfied. Preserve the approved head by writing the final report and completion ledger locally. Report these uncommitted evidence files explicitly and limit them to run status, review reports, or ticket handoff and status updates. For requested PR delivery, push the approved head, include evidence in the PR description, wait for required CI on that head, and report pending human gates as `Awaiting human`.
7. For merge delivery, execute [final merge](references/final-merge.md) after final review. Verify and report the spec and plan status locations for the delivered result. Return only the compact checkpoint defined in [handoff](../feature-orchestrate/references/handoff.md), linking full ticket outcomes, checks, and review reports in run.md. Retain worktrees and chats for inspection. Remove or archive only when requested and after verifying no unpreserved work remains.
